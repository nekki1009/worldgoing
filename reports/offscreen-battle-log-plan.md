# 畫面外戰鬥的戰報與結算：計畫（V0.5）

2026-11-24。Nekki「要補，先排程」（指揮中心串）。

## 0. 一句話

**打起來時，現在只有人會死，沒有戰報、戰功、劫掠與損失結算；本計畫讓這些在畫面外也照常發生。**

V0.4（2026-11-24 晚間）更正：這個缺口不只在畫面外，玩家自己所在的 Site 也一樣，原因見 §1.1。

## 1. 現況（2026-11-24 剿匪全程測試查到）

- 每個 Site 的戰報追蹤器（`site_battle_tracker.gd`）要「這個 Site 正在戰鬥」才會開一場戰鬥，戰鬥安靜 60 遊戲秒後收場並呼叫 `SiteController.close_battle`。
- 實測：5 名官兵在沒人看的山寨殺光 9 名土匪，追蹤器 `open=false`、參與者 0、死亡紀錄空白。

### 1.1 根因（V0.4，2026-11-24 晚間探針實測後更正）

V0.3 把戰報不開和戰鬥計時寫成同一個原因，是沒實測就下的結論，錯了。實際是兩個獨立的錯誤。

**錯誤一：戰報追蹤器在真正的步進裡從來沒被呼叫。**

- `CrowdSite._battle_tick` 只寫在 `step()` 裡「沒有原生工作點」的分支。現在的群眾步進一律走原生工作點（`step_clock_work_point`），事件在 `finish_work_fatigue_point_events` 收尾，那裡沒有呼叫 `_battle_tick`。
- 這個呼叫從 11/06 加入戰報（36f3892）起就在那條分支。
- 實測（`site_battle_tracker_probe_test.gd`，把追蹤器換成計數器）：區域世界 12 步呼叫 0 次、單一 Site 場景 90 步呼叫 0 次，戰鬥中與平時都一樣。
- 所以不分畫面內外、區域世界或單站，戰報與掛在 `close_battle` 的結果都沒有發生過。戰報只有純資料測試（`region_battle_log_test`）。

**錯誤二：區域世界的戰鬥機制用了世界速率，比 TCM 定案快 60 倍。**

- 原生用「步進開始時的戰鬥時鐘」決定戰術速率（`World::tactical_dt`），主機傳的是「步進結束時」的值。區域世界的戰鬥時鐘最多是區間寬度，整步走完時是 0，原生就當成不在戰鬥。單站傳的是 Site 自己的倒數，結束時仍大於 0。
- 實測（同一支探針，戰鬥中逐步量跑步疲勞）：區域世界每遊戲秒 0.1，單站 0.001667，正好 60 倍。
- Nekki 11/15 的 M2 A、M3 A 定的是慢速，所以這是 9b7d3c0 的實作錯誤。
- 走同一段計算、尚未逐項量的：疲勞恢復、擊倒與甦醒、流血、俘虜與逃脫、士氣與潰散。戰鬥中能不能休息、能不能開始訓練，看的也是同一個值。

因此所有戰鬥目前都**沒有**以下結果（勝方聲望不在內，它跟著潰散事件 `team_routed_reputation` 走，正常）：

| 項目 | 來源 |
| --- | --- |
| 戰報（勢力登記簿的 battle log） | `RegionBattleLog.add` |
| 個人戰功、參戰／勝敗紀錄 | `PersonSocialPacket.add_combat_record` |
| 技能：參戰 70 小時計入武藝線與武力 | 技能 K3b |
| 潰散隊伍記憶（7 日後成匪） | `BanditRout.remember` |

| 商隊、收稅隊在戰鬥中覆沒的結算 | `site_caravan.sweep_lost`、`site_tax_envoy.sweep_lost` |
| 開戰時欠餉士氣折扣 | `CrowdSite._arrears_morale` |
| 土匪被官方攻打（熱度 +20） | `SiteBanditAttacked.note_battle` |

| NPC 外交判斷「多久沒有實際開戰」 | `RegionBattleLog.last_fight`（戰報是空的，永遠當成沒打過） |

「土匪被官方攻打」已先用另一條路補上（`SiteBanditAttacked.watch`：每遊戲分鐘看現場人數減員），不依賴戰報。

另一個相關缺口：**全滅的土匪仍留在登記簿**（`status` 還是 `active`、熱度與山寨都在）。接任流程在「沒有自由成員」時直接失敗，沒有把這伙標成已消滅。

## 2. 做法

### 2.0 區域步進改傳 Site 自己的戰鬥時鐘（R0）

- 群眾 Site 在區域步進（即時、冷、補算）裡，傳給原生的戰鬥時鐘改用這個 Site 自己的倒數（`site.combat_left`），和單站同一條路。區間的共用戰鬥秒數照舊只留在時鐘日誌裡。
- 改動點在 `terrain_lab.gd`，**不改 `crowd_site.gd`**（平民圖集指紋檔）、不改原生模組。
- 這是把程式修回 M2 A、M3 A，當錯誤修，不是新的選擇。影響面大，獨立一步配一次全回歸。

### 2.1 追蹤器接上真正的步進（R1）

- 在工作點收尾的地方（`terrain_lab.gd` 的 `_settle_native_checked_point_endpoint`，事件收完之後）用這個 Site 自己的戰鬥時鐘餵追蹤器。改 `terrain_lab.gd`，不改 `crowd_site.gd`。
- 即時 Site 與冷 Site 都會因此開場收場，所以 §2.2 的排隊要和 R1 一起上，不能分開。

### 2.2 收場後果要能在冷 Site 安全執行

`close_battle` 的後果有些會存勢力登記簿（劫掠入寨、商隊覆沒）。冷 Site 在自己的區域點裡不能存登記簿，直接存會被拒絕。

- 做法沿用熱度的排隊方式：先記在控制器上，靜止時（每日掛鉤同一處）再存。
- 補算用的臨時 Site（沒有存檔槽）只寫個人紀錄，不寫戰報、不動登記簿。

### 2.3 全滅的土匪要結束

- 一伙土匪最後一名成員死亡或被俘時，把這伙標成已消滅、清掉山寨。
- 這是剿匪成功：依土匪規格 §6.6，指揮者威望 +3（每伙一次）。

## 4. 風險

- **補算一致性**：同一個 Site 用「綁定的冷 Site 逐步跑」和「補算一次跑完」兩條路，結果必須一樣。戰功寫進人物資料，會進校驗碼；O1 要先確認兩條路都寫、寫得一樣。
- **重複計算**：O0 的人數判定和 O1 的戰報判定會同時成立，已用同一個「每伙每日每 Site 一次」的記號擋住。
- **存檔相容**：只加紀錄，不改既有欄位；舊存檔照讀。
- **效能**：追蹤器每 120 步取樣一次參戰者，冷 Site 多時要量。
- **冷 Site 步進卡死（2026-11-24 發現並修正）**：剿匪全程測試約四場有一場以 `REGION_CROWD_REPLAY_STALLED` 失敗。原因和畫面卡頓無關：
  - 沒有人在工作的隊伍，疲勞由原生引擎自己累計。步進卻會在「可能跑步的人把疲勞帶過 30」的預測時間點切一刀。
  - 戰鬥中被切短的那一步，原生只用 1/60 的速度累計，所以每步只走一小段又被切；跑的人一停，疲勞停在差一點到 30，之後每步都切在同一個 0.0001 遊戲秒的位置，一個 8 秒區間要 7 萬段，上限 4096 段。
  - 修正（`_native_begin_bound`）：原生自己累計的隊伍，戰鬥中不為疲勞跨線切步；平時保留，但只有「可能跑」造成、且近於 0.25 遊戲秒的切點不切。有人工作的隊伍照舊。
  - 專測：`site_crowd_run_band_window_test.gd`。現場紀錄：`output/project_command_center/CONTINUOUS_SWITCH/evidence_stall_20261124`。
- **R0 改變正式遊戲的戰鬥節奏**：區域世界的戰鬥機制會從世界速率回到 TCM 的戰術速率（慢 60 倍）。這是 11/15 以來正式世界的實際表現第一次改變，測試的時間預期也可能要調。見 §1.1、§2.0。
