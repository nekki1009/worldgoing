# 畫面外戰鬥的戰報與結算：計畫（V0.3）

2026-11-24。Nekki「要補，先排程」（指揮中心串）。

## 0. 一句話

**玩家不在的 Site 打起來時，現在只有人會死，沒有戰報、戰功、聲望、劫掠與損失結算；本計畫讓這些在畫面外也照常發生。**

V0.3（2026-11-24 下午）更正：這個缺口不只在畫面外。正式世界（區域世界）裡，玩家自己所在的 Site 也一樣，見 §1.1。

## 1. 現況（2026-11-24 剿匪全程測試查到）

- 每個 Site 的戰報追蹤器（`site_battle_tracker.gd`）要「這個 Site 正在戰鬥」才會開一場戰鬥，戰鬥安靜 60 遊戲秒後收場並呼叫 `SiteController.close_battle`。
- 「正在戰鬥」讀的是步進傳進來的戰鬥時鐘，而且是**這一步結束時還剩多少**。
- 實測：5 名官兵在沒人看的山寨殺光 9 名土匪，追蹤器 `open=false`、參與者 0、死亡紀錄空白。

### 1.1 根因：區域世界的步進把戰鬥時鐘傳成 0（V0.3）

- 區域世界裡，每一步的戰鬥時鐘是「這個區間裡有多少時間在戰鬥」，最多就是區間自己的寬度；而且是全世界共用（任何一個 Site 在打，所有 Site 的區間都算戰鬥）。
- 傳給原生群眾與戰報追蹤器的是「步進結束時還剩多少」＝區間寬度減去步進長度。整個區間一步走完時就是 **0**。
- 單一 Site 的測試場景不走區域步進，戰鬥時鐘是該 Site 自己的倒數（最後一次接觸後 20 秒），結束時還大於 0，所以一切正常。戰報只有純資料測試（`region_battle_log_test`），沒有任何測試在區域世界裡真的打一場再檢查戰報，所以一直沒被發現。
- 依程式判讀（尚未實測），區域世界裡只有兩種步進會讓追蹤器看到戰鬥：這一步有弓箭齊射（齊射自己帶 20 秒的戰鬥標記），或這一步被別的原因切短。純近戰、整步走完時看不到。
- 實測（`site_crowd_run_band_window_test.gd`，區域世界、玩家所在的 Site、Site 自己的戰鬥時鐘維持在 30）：40 遊戲秒後追蹤器 `open=false`。

同一個 0 也餵給原生群眾，造成兩個後果：

| 後果 | 現況 | 設計 |
| --- | --- | --- |
| 戰鬥機制的計時（跑步疲勞、疲勞恢復、擊倒與甦醒、流血、俘虜進度、士氣觀察） | 世界速率，戰鬥中 1 行動秒算 60 遊戲秒 | TCM（Nekki 11/15 M2、M3 選 A）：戰鬥中維持 1 行動秒＝1 遊戲秒，打起來的感覺和以前一樣 |
| 戰鬥中能不能休息恢復疲勞、能不能開始訓練 | 原生看到的戰鬥時鐘是 0，當成不在戰鬥 | 戰鬥中不行 |

跑步疲勞已量到是世界速率（一人跑 6 遊戲秒，6 人隊伍 +0.1；戰術速率應為 +0.0017）。其餘各項依同一段原生程式推定，尚未逐項量。

因此冷 Site 的戰鬥目前**沒有**以下結果（全部掛在 `close_battle`）：

| 項目 | 來源 |
| --- | --- |
| 戰報（勢力登記簿的 battle log） | `RegionBattleLog.add` |
| 個人戰功、參戰／勝敗紀錄 | `PersonSocialPacket.add_combat_record` |
| 技能：參戰 70 小時計入武藝線與武力 | 技能 K3b |
| 勝方隊長聲望 | `Reputation.victory_gain` |
| 潰散隊伍記憶（7 日後成匪） | `BanditRout.remember` |
| 土匪劫掠得手後搬走倉庫存貨 | `BanditAftermath.after_battle` |
| 商隊、收稅隊在戰鬥中覆沒的結算 | `site_caravan.sweep_lost`、`site_tax_envoy.sweep_lost` |
| 開戰時欠餉士氣折扣 | `CrowdSite._arrears_morale` |
| 土匪被官方攻打（熱度 +20） | `SiteBanditAttacked.note_battle` |

最後一項已先用另一條路補上（`SiteBanditAttacked.watch`：每遊戲分鐘看現場人數減員），不依賴戰報。

另一個相關缺口：**全滅的土匪仍留在登記簿**（`status` 還是 `active`、熱度與山寨都在）。接任流程在「沒有自由成員」時直接失敗，沒有把這伙標成已消滅。

## 2. 做法

### 2.0 區域步進改傳 Site 自己的戰鬥時鐘（R0，V0.3 新增）

- 每個 Site 自己的戰鬥時鐘本來就有（`site.combat_left`：原生每步回報接觸就補到 20 秒，Site 的時鐘每步倒數），存檔與補算都帶著它。
- 做法：群眾 Site 在區域步進（即時與冷 Site、補算）裡，傳給原生和追蹤器的戰鬥時鐘改用這個 Site 自己的倒數，和單一 Site 場景同一條路。區間的共用戰鬥秒數照舊只留在時鐘日誌裡，不再拿來當原生的戰鬥時鐘。
- 這樣一次解決三件事：追蹤器在即時與冷 Site 都會開場收場；戰鬥機制回到 TCM 的戰術速率；戰鬥中不再被當成可以休息。
- 改動點在 `terrain_lab.gd`（步進決定戰鬥時鐘的三處），**不改 `crowd_site.gd`**（平民圖集指紋檔）、不改原生模組。
- 影響面大：區域世界裡所有戰鬥的節奏會變慢 60 倍（回到 TCM 定案的樣子），許多以區域世界跑戰鬥的測試的時間預期要跟著看。要當成獨立的一步，配一次全回歸。

### 2.1 追蹤器在冷 Site 也要開

- R0 之後追蹤器會自己開場。冷 Site 剩下的問題是收場後果怎麼安全執行（§2.2）。

### 2.2 收場後果要能在冷 Site 安全執行

`close_battle` 的後果有些會存勢力登記簿（劫掠入寨、商隊覆沒）。冷 Site 在自己的區域點裡不能存登記簿，直接存會被拒絕。

- 做法沿用熱度的排隊方式：先記在控制器上，靜止時（每日掛鉤同一處）再存。
- 補算用的臨時 Site（沒有存檔槽）只寫個人紀錄，不寫戰報、不動登記簿。

### 2.3 全滅的土匪要結束

- 一伙土匪最後一名成員死亡或被俘時，把這伙標成已消滅、清掉山寨。
- 這是剿匪成功：依土匪規格 §6.6，指揮者威望 +3（每伙一次）。

## 4. 風險

- **補算一致性**：同一個 Site 用「綁定的冷 Site 逐步跑」和「補算一次跑完」兩條路，結果必須一樣。戰功寫進人物資料，會進校驗碼；O1 要先確認兩條路都寫、寫得一樣。
- **重複計算**：O0 的人數判定和 O1 的戰報判定會同時成立，已用同一個「每伙每日每 Site 一次」的記號擋住。
- **存檔相容**：只加紀錄，不改既有欄位；舊存檔照讀。
- **效能**：追蹤器每 120 步取樣一次參戰者，冷 Site 多時要量。
- **冷 Site 步進卡死（2026-11-24 發現並修正）**：剿匪全程測試約四場有一場以 `REGION_CROWD_REPLAY_STALLED` 失敗。原因和畫面卡頓無關：
  - 沒有人在工作的隊伍，疲勞由原生引擎自己累計。步進卻會在「可能跑步的人把疲勞帶過 30」的預測時間點切一刀。
  - 戰鬥中被切短的那一步，原生只用 1/60 的速度累計，所以每步只走一小段又被切；跑的人一停，疲勞停在差一點到 30，之後每步都切在同一個 0.0001 遊戲秒的位置，一個 8 秒區間要 7 萬段，上限 4096 段。
  - 修正（`_native_begin_bound`）：原生自己累計的隊伍，戰鬥中不為疲勞跨線切步；平時保留，但只有「可能跑」造成、且近於 0.25 遊戲秒的切點不切。有人工作的隊伍照舊。
  - 專測：`site_crowd_run_band_window_test.gd`。現場紀錄：`output/project_command_center/CONTINUOUS_SWITCH/evidence_stall_20261124`。
- **R0 改變正式遊戲的戰鬥節奏**：區域世界的戰鬥機制會從世界速率回到 TCM 的戰術速率（慢 60 倍）。這是 11/15 以來正式世界的實際表現第一次改變，測試的時間預期也可能要調。見 §1.1、§2.0。
